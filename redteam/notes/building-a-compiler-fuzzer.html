Building a Compiler Fuzzer, From Scratch

A walkthrough that shows how to red-team a compiler. Generate well-typed programs and run them on both backends. Then let mismatches and panics find the bugs.

Written for one reader who wants to rebuild this system by hand. It is a companion to the redteam/ directory in the Gleam compiler repository.

1. Why fuzz a compiler, and what "red teaming" means here

A compiler is software. It takes a program and produces other software. A compiler bug does not usually crash loudly. The compiler silently generates code that does the wrong thing. Or it panics deep in a code path that nobody imagined. These are the worst bugs. The program type-checks. The program builds. Then it misbehaves quietly. Or the build crashes in a way that the user cannot explain.

The premise of compiler red teaming is simple. It is almost naive:

Throw a large number of valid, well-typed programs at the compiler. Use every backend that the compiler supports. Then check two things. The compiler must never panic. Every backend must compute the same answer.

From that sentence come two oracles:

OracleQuestion it answersNeeds
Crash oracle "Does the compiler ever panic, on any input?" Feed millions of inputs, catch panics.
Differential oracle "Do the Erlang and JavaScript backends agree?" Compile each program for both backends. Run both. Compare the output.

That is the entire idea. The rest of this document is the engineering that makes the two oracles fast, deterministic, and trustworthy. Gleam is a good target because it has two backends. The two backends can disagree. With two backends, we get a differential oracle for free. Most single-backend languages cannot have one.

A founding observation. The phrase "valid, well-typed programs" carries the main idea. If you throw random bytes at a compiler, you hit only the parser. The parser is the most tested part. It is also the least interesting part. The bugs you want live in the type checker and the code generators. To reach them, you need inputs that parse and type-check. That is the hard problem. It is the centerpiece of this setup.

What did this find? During the build, the machinery found five bugs. One is a parser panic. One is an Erlang decision-tree panic. One is an Erlang type-name hygiene bug. Two are JavaScript bit-array codegen bugs. Several are silent miscompilations. Erlang and JavaScript simply disagreed about the answer. That is the payoff. The programs look fine. They build fine. They are wrong.

2. The architecture at a glance

Draw the whole system before you build any part. There are two pipes. They share one trunk.

# The shared trunk: a deterministic generator turns a number into a program
seed ──▶ gleam-smith (Module::from_seed(n)) ──▶ Gleam source text

# Pipe A: the crash oracle (millions of inputs, in-process, fast)
seed ──▶ gleam-smith ──▶ source ──▶ probe (parse→analyse→codegen) ──▶ panic? → artifact

# Pipe B: the differential oracle (thousands of inputs, spawns the real compiler)
seed ──▶ gleam-smith ──▶ source ──▶ gleam run -t erlang ─┐
                             └─▶ gleam run -t javascript ─┼─▶ compare normalised stdout ──▶ bug?

The two pipes have very different needs. Much of the design follows from that difference:

  • Pipe A must be fast. libFuzzer is a coverage-guided fuzzer. It works only when the code under test runs in-process. The code must run in microseconds. If you spawn the gleam binary for each input, the run takes about 300 ms. That is about 300 times too slow. Coverage-guided fuzzing then has no value. Pipe A needs a small in-process hook into the compiler. This hook is the probe.
  • Pipe B must use the real compiler. To detect miscompilations, the actual compiler must do the actual work. A reimplementation is not enough. Pipe B calls the real gleam binary. The method is slower. That is acceptable. You run a few thousand programs. You do not run millions.

This is the file map that you will end up with. All files live in the Gleam repository under redteam/ and fuzz/:

redteam/
  smith/src/lib.rs          # the generator (the heart)
  smith/src/main.rs         # `gen ` / `batch   ` CLI
  bin/diff-run.sh           # orchestration: spawn both backends, call the normaliser
  bin/smith-campaign.sh     # run many seeds, keep divergences
  bin/version-check.sh      # does this finding reproduce on a release?
  diff/src/lib.rs           # the normaliser (Rust, unit tested)
  diff/src/main.rs          # redteam-diff: compare command + report
  ops/fuzz-loop.sh          # the infinite VPS loop
  ops/process-artifacts.sh  # dedup crash artifacts after each sprint
  ops/sync-job.sh           # daily git pull + rebuild + corpus tidy
  ops/install-systemd.sh    # install the systemd units
  corpus/*.gleam            # hand-written seeds feeding the fuzzer
  findings.md               # the journal of every bug found
compiler-core/src/redteam.rs  # the in-process probe (Pipe A)
fuzz/
  fuzz_targets/parse_only.rs          # lexer/parser never panics
  fuzz_targets/compile_all_targets.rs # full pipeline never panics
  fuzz_targets/smith_compile.rs       # generator-driven full pipeline
  Cargo.toml                          # cargo-fuzz crate
Why the probe lives in the compiler repo. The probe calls the internal APIs of the compiler directly. The APIs are parse::parse_module, the module analyser, erlang::module, and javascript::module. These are not public APIs. External code cannot call them. To use a separate repository, you must expose the APIs. Or you must accept a slower crash oracle that spawns the binary. That is a real trade-off. The lessons section describes it.

Build the system from the bottom up. Build the probe first. Then build the generator. Then build the two loops. Then build the operations glue.

3. The crash oracle: a tiny in-process "probe"

The probe is a small module inside the compiler. It runs the pipeline and reports what happened. The pipeline parses, analyses for a target, and generates code. Its contract is one sentence:

The compiler must never panic, on any input. Invalid inputs produce a parse error or an analysis rejection. Anything else is a bug.

The public surface is one enum and a few functions:

compiler-core/src/redteam.rs 
// What happened when we pushed an input through the compiler pipeline.
pub enum ProbeOutcome {
    InputTooLarge,
    NotUtf8,
    ParseError,                          // invalid program, rejected by parser
    AnalysisRejected { target: &'static str }, // rejected by the type checker
    ParsedOk,                            // parser-only probe
    Compiled {
        javascript_bytes: usize,
        typescript_bytes: usize,
        erlang_bytes: usize,
    },                                   // the whole pipeline succeeded
}

The workhorse is probe_bytes. It checks the size of the input. It checks that the input is valid UTF-8. Then it runs the pipeline on the input. The catch_unwind wrapper captures a panicking compiler as evidence. The evidence is a string. The compiler does not die. This lets you replay, shrink, and label a crash:

// Catch any compiler panic and return it as a string payload, so corpus
// replay and triage tooling can report it as evidence instead of dying.
pub fn probe_guarded(data: &[u8]) -> Result<ProbeOutcome, String> {
    std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| probe_bytes(data)))
        .map_err(|payload| panic_payload_to_string(&payload))
}

The two compile_* functions do all the real work. This is the Erlang one. It analyses the module. Then it sends the module to the Erlang code generator:

// Compile a single module to Erlang. Returns None if rejected by the
// analyser. May only panic on a genuine compiler bug.
pub fn compile_erlang(src: &str) -> Option<String> {
    let (typed, line_numbers) = analyse(src, Target::Erlang)?;
    Some(erlang::module(&typed, line_numbers, Utf8Path::new("redteam/root")))
}

The analyse function needs your attention. It sets up the prelude. It runs the module analyser. It mirrors what the real build does:

fn analyse(src: &str, target: Target) -> Option<(TypedModule, LineNumbers)> {
    let ids = UniqueIdGenerator::new();
    let mut modules = im::HashMap::new();
    let _ = modules.insert(PRELUDE_MODULE_NAME.into(), type_::build_prelude(&ids));

    let mut ast = parse_ok(src)?;      // if it doesn't parse, we're done
    ast.name = "redteam/probe".into();

    let outcome = ModuleAnalyzerConstructor::<()> {
        target,
        ids: &ids,
        origin: Origin::Src,
        importable_modules: &modules,
        warnings: &TypeWarningEmitter::null(),
        target_support: TargetSupport::NotEnforced,
        ..
    }
    .infer_module(ast, LineNumbers::new(src), "src/redteam_probe.gleam".into());

    // Only fully-successful analysis reaches codegen, mirroring the real
    // build pipeline. A PartialFailure carries analysis errors; codegen on
    // such a module is unreachable in practice.
    match outcome {
        Outcome::Ok(typed) => Some((typed, LineNumbers::new(src))),
        Outcome::PartialFailure(..) | Outcome::TotalFailure(_) => None,
    }
}
Golden rule: the probe must mirror the real pipeline exactly. This is the main source of false findings. Early on, the probe ran an inline module pass. The real build pipeline does not run this pass. Inlining is disabled upstream. The result was two false bugs. They never reproduced on the real compiler. They were artifacts of the probe. The probe did something different from production. If the probe and the real build ever disagree, the probe is wrong. This one lesson has cost more time than any fuzzer bug.

The last piece of the probe is a known-bug classifier. Once you confirm a bug, you do not want to rediscover it forever. You want new bugs to stand out. So there is a small function. It says that the panic is one we already know about:

// Panic signatures of CONFIRMED compiler bugs. Fuzz harnesses treat these
// as expected: skipping them avoids rediscovering known bugs forever, while
// any NEW panic signature still gets reported.
pub fn is_known_compiler_bug(panic: &str) -> bool {
    panic.contains("Token could not be converted to binop") // parser panic
        || panic.contains("variable not in scope")           // erlang codegen panic
}

That is the whole probe. It is about 150 lines. Now we move to the interesting part.

4. The heart: a well-typed program generator

This is the part that needs your real thought. The probe and the diff runner are plumbing. The generator is the brain. It is the difference between fuzzing the parser and fuzzing the compiler.

4.1 The core idea: generate for a type, not just anything

A naive generator makes random syntax. Most of the syntax fails to type-check. That wastes fuzz budget. The compiler rejects these inputs before codegen. The fix is to make the generator reason about types. The fix comes from wasm-smith. wasm-smith generates valid Wasm modules by construction:

Do not ask the generator to make a random expression. Ask it to make an expression of type Int. The generator picks only things that produce an Int. To make an Int, pick from three choices. Pick an integer literal. Pick a variable that is already bound to an Int. Pick an arithmetic expression such as a + b, where both parts are Int.

The generator is a small type checker that runs backwards. You give it a required type. It produces a term of that type. It never refers to a variable that is not in scope. That is what "well-typed by construction" means. That is the whole trick.

The generator needs three things:

  1. An AST. The AST gives the shapes of programs that the generator can make.
  2. A type environment. The environment holds the in-scope variables and their types.
  3. A gen function. The call gen(env, type) returns an expression. The function is a large, honest match on the type.

4.2 The types and the AST, kept boring

A good generator AST is minimal and readable. This version gives you your first real bugs. The real repository has grown more variants: floats, bit arrays, and constants. This is the clean core. The pattern extends without new ideas.

redteam/smith/src/lib.rs (conceptual core) 
// The types the generator can produce. Kept deliberately small so the
// generation logic stays comprehensible: "for this type, what can I make?"
enum Ty {
    Int,
    String,           // "String" is a reserved word in Rust, so Gleam's smith uses Str
    Bool,
    List(Box<Ty>),    // a list of elements of some type
    Tuple(Box<Ty>, Box<Ty>),
    Custom(usize),    // index into the module's generated custom types
}

// The AST. One variant per thing the generator knows how to say.
enum Expr {
    IntLit(i64),
    StrLit(String),
    BoolLit(bool),
    Var(String),                       // a reference to an in-scope variable
    ListLit(Vec<Expr>),
    TupleLit(Box<Expr>, Box<Expr>),
    BinOp(BinOp, Box<Expr>, Box<Expr>),
    If { cond: Box<Expr>, then: Box<Expr>, else_: Box<Expr> },
    Case { subject: Box<Expr>, clauses: Vec<Clause> },
    Call { name: String, args: Vec<Expr> },   // call a generated function
}
Human judgment: keep it boring. The production generator has some clever machinery. It uses weighted random choice. It uses shadowing bias pools. It uses a bind-a-specific-name spec for alternative patterns. It uses bit-array segment options. That cleverness is earned later. A real bug must demand it. Do not start there. Start with a generator where you can explain each function to a colleague in one sentence. You can always add cleverness when a real bug demands it. The lesson log at the end shows where the cleverness outran the value.

4.3 The type environment

The environment is a stack of pairs. Each pair is a name and a type. When you generate a binding, push the new pair. A binding can be a let x = <expr>. It can be a function parameter. It can be a case clause that binds a name. When you need an expression of a type, look at what is in scope for that type:

redteam/smith/src/lib.rs 
// The environment: names currently bound, and their types.
type Env = Vec<(String, Ty)>;

// `gen_expr` looks here when it wants a variable of the required type.
fn vars_of_type(env: &Env, ty: &Ty) -> Vec<&String> {
    env.iter()
        .filter(|(_, t)| t == ty)
        .map(|(n, _)| n)
        .collect()
}

4.4 The generator function: one big honest match

This is the function that everything depends on. It takes the environment. It takes a required type. It takes a depth budget. The depth budget stops infinite recursion. It stops the stack from overflowing on nested expressions. The function returns an expression of the required type.

redteam/smith/src/lib.rs (conceptual) 
fn gen_expr(env: &Env, ty: &Ty, depth: u8) -> Expr {
    // Depth guard: at the bottom, fall back to something atomic.
    if depth == 0 {
        return gen_atomic(env, ty);
    }

    // When picking how to build a value of this type, we only offer choices
    // that are guaranteed to produce the right type. This is the whole
    // "well-typed by construction" trick: the type of the RESULT is never in
    // question, because we derive it from the required type.
    match ty {
        Ty::Int => pick_int_expr(env, depth),           // literal | var | a+b | a-b | ...
        Ty::String => pick_string_expr(env, depth),     // literal | var | concat
        Ty::Bool => pick_bool_expr(env, depth),         // literal | var | comparison | !
        Ty::List(inner) => gen_list_expr(env, inner, depth),
        Ty::Tuple(a, b) => gen_tuple_expr(env, a, b, depth),
        Ty::Custom(idx) => gen_custom_expr(env, idx, depth),
    }
}

Each helper is a small function. For example, an Int expression can be one of three things. It can be an integer literal. It can be a reference to an in-scope Int variable. It can be an arithmetic operation. The operands are then Int expressions:

// All the ways to build an Int. Each recursive gen_expr is asked for an Int,
// so the result is guaranteed to be an Int.
fn pick_int_expr(env: &Env, depth: u8) -> Expr {
    let option = roll(&[40, 30, 30]);   // weighted choice, 0..=2
    match option {
        0 => Expr::IntLit(int_pool()),                   // a literal
        1 => {
            // a variable already in scope, if there's a suitable one
            let vars = vars_of_type(env, &Ty::Int);
            if vars.is_empty() { gen_other_int(env, depth) }
            else { Expr::Var(vars[0].clone()) }
        }
        _ => {
            // a + b, a - b, a * b — operands generated recursively
            let op = pick(&["+", "-", "*"]);
            let a = gen_expr(env, &Ty::Int, depth - 1);
            let b = gen_expr(env, &Ty::Int, depth - 1);
            Expr::BinOp(op, Box::new(a), Box::new(b))
        }
    }
}

Note how the recursion pins the type at every level. The call gen_expr(env, &Ty::Int, …) generates the operands. It guarantees that the operands are Int. So a + b is an Int. There can be no type errors. Nesting depth does not matter. This property makes the generator safe to run on millions of inputs. Generated code must compile. If a generated program does not compile, that is a generator bug. The crash loop catches it. See section 5.

4.5 Functions and main

A program has more than one expression. It has functions with parameters. It has a main function that echoes values. The generator builds a few functions. Each function has typed parameters. Each function has a body that the generator builds as above. Then the generator builds a main function. The main function holds echo <expr> statements.

redteam/smith/src/lib.rs (conceptual) 
struct FnSig {
    name: String,
    params: Vec<(String, Ty)>,   // named, typed parameters
    ret: Ty,
}

fn gen_function(ctx: &mut Ctx) -> (FnSig, Expr) {
    // Build the signature: parameters flow into the environment, so the
    // body can use them.
    let mut env: Env = Vec::new();
    let mut params = Vec::new();
    for _ in 0..param_count() {
        let pty = gen_any_type(ctx);               // pick a param type
        let pname = ctx.fresh("p");                // p0, p1, p2
        env.push((pname.clone(), pty.clone()));
        params.push((pname, pty));
    }

    let ret = gen_any_type(ctx);                   // the return type
    let name = ctx.fresh("f");                     // f0, f1, f2
    let body = gen_expr(&env, &ret, 3);            // generate the body
    (FnSig { name, params, ret }, body)
}

And main echoes a few generated values of supported echoable types:

fn gen_main(ctx: &mut Ctx) -> Vec<Stmt> {
    // 1-4 echo statements; each echoes a value of a known-printable type so
    // the cross-backend output is comparable (see the differential section).
    let mut main = Vec::new();
    for _ in 0..=int_range(1, 4) {
        let ty = pick(&[Ty::Int, Ty::String, Ty::Bool, Ty::List(Box::new(Ty::Int))]);
        let expr = gen_expr(&[], &ty, 3);
        main.push(Stmt::Echo(expr));
    }
    main
}
Why constrain what echo prints? The differential oracle compares stdout across backends. Some things render differently. For example, Erlang and JS format a bit-array differently. They format a float differently. If you echo such a value, you get noise. The mismatch looks real but it is not a bug. Keep the echoed types to the ones both backends render identically. This keeps the signal clean. It is a trust-the-oracle decision. Section 6 discusses it.

4.6 Rendering: from AST to source text

Once you have a Module, you pretty-print it. The renderer walks the AST and writes Gleam source. The work is mechanical. There is one match arm per AST node. There is one real trap. Gleam has no (expr) grouping syntax. To avoid precedence bugs, wrap non-atomic operands in { } blocks.

redteam/smith/src/lib.rs (conceptual) 
fn write_expr(out: &mut String, e: &Expr, ind: usize) {
    match e {
        Expr::IntLit(n) => out.push_str(&n.to_string()),
        Expr::Var(name) => out.push_str(name),
        Expr::BinOp(op, a, b) => {
            // Operands that aren't atomic get wrapped in {} to fix precedence.
            write_operand(out, a, ind);
            out.push(' ');
            out.push_str(op);
            out.push(' ');
            write_operand(out, b, ind);
        }
        // ... every other node ...
    }
}

// Wrap non-atomic expressions in {} so binops don't accidentally parse
// with the wrong precedence.
fn write_operand(out: &mut String, e: &Expr, ind: usize) {
    if is_atomic(e) { return write_expr(out, e, ind); }
    out.push('{');
    write_expr(out, e, ind + 1);
    out.push('}');
}

4.7 Determinism: a seed reproduces a program

Get one property right early. The same seed must always produce the same program. If generation were random, you cannot shrink a bug. You cannot bisect it. You cannot file a reproducible report. The generator does not use a global RNG. It consumes a byte stream. The byte stream comes from the seed. Every random choice reads bytes from that stream.

redteam/smith/src/lib.rs 
// Deterministic generation from a 64-bit seed: expand the seed into a byte
// stream that the Arbitrary implementation drivess from. Same seed, same
// bytes, same program — forever.
pub fn from_seed(seed: u64) -> Module {
    let mut state = seed ^ 0x9E37_79B9_7F4A_7C15;
    let mut bytes = vec![0u8; 2048];
    for _ in 0..8 {
        for chunk in bytes.chunks_mut(8) {
            state ^= state << 13;
            state ^= state >> 7;
            state ^= state << 17;
            let le = state.to_le_bytes();
            chunk.copy_from_slice(&le[..chunk.len()]);
        }
        let mut u = Unstructured::new(&bytes);
        if let Ok(m) = Module::arbitrary(&mut u) {
            return m;
        }
    }
    // Unreachable in practice; a tiny fallback module.
    fallback_module()
}

The Unstructured cursor turns bytes into values. The call u.int_in_range(0..=9) reads bytes and returns a number in that range. The call pick(u, xs) chooses an element. The mapping is pure. The same bytes in give the same value out. The seed produces the same bytes every time. So the whole process is reproducible. This also lets libFuzzer mutate a seed meaningfully. See section 5.

In the real repository, the generator implements the Rust Arbitrary trait. Raw fuzz bytes can then drive the generator directly. The fuzz bytes come from libFuzzer. The function from_seed is a thin, seed-first helper. It uses the same logic. One implementation serves both the CLI and the fuzzer.

4.8 The CLI that makes it usable by hand

redteam/smith/src/main.rs (complete, it is short) 
//! gleam-smith CLI: generate deterministic Gleam programs from seeds.
//!   gleam-smith gen                 print one program to stdout
//!   gleam-smith batch      write seed_.gleam files

use gleam_smith::Module;

fn main() {
    let args: Vec<String> = std::env::args().collect();
    let usage = "usage:\n  gleam-smith gen \n  gleam-smith batch   ";
    match args.get(1).map(String::as_str) {
        Some("gen") => {
            let seed = args.get(2).and_then(|s| s.parse().ok()).unwrap_or_else(|| {
                eprintln!("{usage}"); std::process::exit(2)
            });
            print!("{}", Module::from_seed(seed).to_source());
        }
        Some("batch") => {
            let (Some(dir), Some(start), Some(count)) = (args.get(2), args.get(3), args.get(4))
            else { eprintln!("{usage}"); std::process::exit(2) };
            let start = start.parse().expect("start seed");
            let count = count.parse().expect("count");
            std::fs::create_dir_all(dir).expect("create output dir");
            for seed in start..start + count {
                let src = Module::from_seed(seed).to_source();
                std::fs::write(format!("{dir}/seed_{seed}.gleam"), src).expect("write");
            }
            println!("wrote {count} programs to {dir}");
        }
        _ => { eprintln!("{usage}"); std::process::exit(2) }
    }
}
Try it right now. With this code, you can produce well-typed Gleam programs. Throw them at the real compiler by hand. 
cargo run -p gleam-smith -- gen 42 | tee /tmp/p.gleam
gleam build --target erlang     # does it compile? build clean?
gleam build --target javascript # does the other backend agree?
The manual loop below is the start of the whole automated rig. Everything from here makes the rig faster and more systematic.

5. Feeding it to a fuzzer: the crash loop

Now you automate Pipe A with libFuzzer. You use cargo-fuzz. libFuzzer is a coverage-guided engine. It runs your target function millions of times. It keeps the inputs that hit new code coverage. It mutates these inputs to explore further. It is the correct engine for the question: does the compiler ever panic.

The crate stays out of the main workspace on purpose. Fuzz builds need a nightly toolchain. They need sanitizer instrumentation. Write one file per target:

fuzz/fuzz_targets/parse_only.rs (complete) 
// Fuzz target: the lexer and parser must never panic, on any byte sequence.
// Kept cheap and fast so it runs at the highest rate possible.
#![no_main]

use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    let _ = gleam_core::redteam::probe_parse_bytes(data);
});
fuzz/fuzz_targets/compile_all_targets.rs (complete) 
// Fuzz target: parse -> analyse -> codegen for BOTH targets.
// The contract is the compiler never panics and never reaches codegen with
// an invalid internal state. Any panic is a bug; libFuzzer saves the
// reproducing input to artifacts/.
#![no_main]

use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    let _ = gleam_core::redteam::probe_bytes(data);
});
fuzz/fuzz_targets/smith_compile.rs (complete) 
// Fuzz target: raw bytes drive gleam-smith to build a well-typed module,
// then the FULL pipeline runs on it. This is the target that reaches the
// codegen bug classes (decision trees, hygiene) that text-mutation fuzzing
// almost never reaches.
// Two panic kinds are caught:
// - compiler panics on generated programs -> COMPILER BUGS (saved by libFuzzer)
// - generated program doesn't compile     -> GENERATOR BUGS (raised below)
#![no_main]

use gleam_smith::Module;
use libfuzzer_sys::arbitrary::{Arbitrary, Unstructured};
use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    let mut u = Unstructured::new(data);
    let Ok(module) = u.arbitrary::<Module>() else {
        return;
    };
    let src = module.to_source();
    match gleam_core::redteam::probe_source(&src) {
        gleam_core::redteam::ProbeOutcome::Compiled { .. } => {}
        other => panic!("gleam-smith generated non-compiling program ({other}):\n{src}"),
    }
});
Why three targets? Each target is progressively heavier.
  • parse_only: this is the cheapest target. It runs fastest. It checks only the parser. The parser panic for const b = 1 |> 2 appeared here. The input was a raw-text mutation. It needed no generator.
  • compile_all_targets: this target runs the full pipeline on arbitrary text. It catches panics from any text that looks syntactically valid.
  • smith_compile: this target runs the full pipeline on generated well-typed code. It reaches the deep codegen bugs. The text-only targets cannot reach them.
The smith_compile target has a hidden benefit. If the generator makes a program that does not compile, the target panics. libFuzzer saves the input as an artifact. So the fuzzer enforces the valid-by-construction contract of the generator.

Run them with nightly Rust:

# per-target corpus dirs grow as coverage is discovered
cargo +nightly fuzz run smith_compile fuzz/corpus/smith_compile -- -max_total_time=3600 -timeout=25
cargo +nightly fuzz run compile_all_targets -- -max_total_time=3600 -timeout=25
cargo +nightly fuzz run parse_only -- -max_total_time=900 -timeout=10

When it finds a panic, it saves the input in fuzz/artifacts/<target>/. Then minimize the input. libFuzzer does this with -minimize_crash. Then reduce the input by hand. Find the smallest program that still panics. This is what you file as a bug.

Two failure modes, do not confuse them.
  1. A compiler panic on generated code is a real compiler bug. It is gold.
  2. Generated code that does not compile means a generator bug. The generator violated its contract. Fix the generator. Do not file it against the compiler.
The panic hook of libFuzzer fires before any in-process catch_unwind. So both kinds become artifacts. Look at the input to tell them apart. If a generated program fails to compile, the generator is wrong. If a well-formed program panics, the compiler is wrong. Keep this distinction in mind during triage. See section 8.

6. The differential oracle: run it on both backends

The crash oracle finds panics. The differential oracle finds a scarier class. These programs build fine. They run differently on the two backends. This oracle found the JavaScript bit-array miscompilations. Those bugs are silent. There is no crash. There is only a wrong answer on one backend.

The runner is a shell script. It orchestrates processes. Its core is simple. Compile the program for both backends. Run both programs. Send the raw output to the normaliser. Compare the results.

The split is deliberate. The shell script spawns processes: it builds the temp project and runs gleam twice. All the text processing lives in Rust. The Rust tool is called redteam-diff. It normalises the two raw outputs, decides the verdict, prints the report, and sets the exit code. The bash script keeps only the orchestration, because spawning processes with timeouts is bash territory. The normaliser is text parsing, so it gets unit tests.

redteam/bin/diff-run.sh (essence) 
#!/usr/bin/env bash
set -uo pipefail

INPUT="${1:?usage: diff-run.sh }"

WORK="$(mktemp -d)"
trap 'rm -rf "$WORK"' EXIT
mkdir -p "$WORK/src"
cp "$INPUT" "$WORK/src/main.gleam"
printf 'name = "redteam_case"\n' > "$WORK/gleam.toml"

run_target() {   # $1 = target; echo writes to stderr, captured and normalised
  (cd "$WORK" && gleam run --target "$1" --module main) >"$WORK/$1.raw" 2>&1
}

run_target erlang;      ERLANG_STATUS=$?
run_target javascript;  JS_STATUS=$?

# Everything textual — normalise, verdict, report, exit code — happens in Rust.
redteam-diff compare --input "$INPUT" \
  "$WORK/erlang.raw" "$WORK/javascript.raw" "$ERLANG_STATUS" "$JS_STATUS"
exit $?

The normaliser: the hard, boring, essential part

There is a trap. Gleam prints build progress to stderr. It prints warnings to stderr. It prints source-location markers to stderr. It prints diagnostic prose to stderr. All of this mixes with the echo output of the program. If you diff the raw output, almost every program shows a mismatch. That is pure noise. The normaliser strips everything except the value-shaped lines. These are the lines the program actually printed.

This is where you make the trust-the-oracle decisions. For example, Erlang prints the float 1.0. JS prints 1. JS drops a trailing .0. That is a rendering difference. It is not a bug. The normaliser canonicalises whole-valued floats. It strips the trailing .0. Then 1.0 and 1 compare equal.

redteam/diff/src/lib.rs (the normaliser) 
// Normalise: strip ANSI codes, drop warning blocks, drop the echo
// source-location line, then WHITELIST only value-shaped lines.
// A whitelist (not a blacklist) is the robust choice: Gleam emits many
// diagnostic prose forms (Hint:, multi-line messages, carets) that are
// fragile to blacklisting; keeping only values keeps the signal clean.
fn normalise(&self, raw: &str) -> Vec<String> {
    let mut lines = Vec::new();
    let mut in_warning = false;
    for line in raw.lines() {
        let line = self.ansi.replace_all(line, "").into_owned();

        // Warning blocks: a `warning:` line starts a block that
        // continues until (and includes) the next blank line.
        if in_warning {
            if line.trim_end().is_empty() { in_warning = false; }
            continue;
        }
        if line.starts_with("warning:") { in_warning = true; continue; }

        // Drop the per-target echo source-location line.
        if self.echo_location.is_match(&line) { continue; }

        // Keep only value-shaped lines.
        if !self.value_shape.is_match(&line) { continue; }

        // Canonicalise whole-valued floats so both backends agree.
        let line = self.whole_float.replace_all(&line, "$1").into_owned();
        let line = self.trailing_ws.replace_all(&line, "").into_owned();
        lines.push(line);
    }
    lines
}
Why Rust, not bash? This function was once an awk/sed/grep pipeline. The pipeline did the same work but had no tests and silent failure modes. The Rust version is unit tested: each stage (ANSI, warning blocks, echo location, whitelist, float canonicalisation, trailing whitespace) has its own test in redteam/diff/src/lib.rs. The process spawning stayed in bash, where it is the easier tool. This is the one piece of the rig that crossed from orchestration into logic, so it is the one piece that earned a real implementation.

Now I unpack the whitelist regex. It is the product of real experience. ^-?[0-9]+$ is an integer. ^-?[0-9]+\.[0-9]+$ is a float. ^".*"$ is a string. ^(True|False)$ is a bool. ^\[.*\]$ is a list. ^#\(.*\)$ is a tuple. ^<<.*>>$ is a bit array. ^[A-Z][A-Za-z0-9_]*(\(.*\))?$ is a constructor. Only lines with these shapes are the program output. Everything else is build noise. The normaliser drops it on both sides.

Why a whitelist and not a blacklist? The first idea is to blacklist the known noise. Strip any warning: line. Strip the progress lines. But the diagnostics of Gleam come in many shapes. They include hints, multi-line messages, carets, and colour codes. New shapes keep appearing. Blacklisting becomes a fight with no end. Whitelisting keeps only what looks like a value. Whitelisting is stable. It does not matter what new noise the compiler emits. The noise never looks like a value.
Trust the oracle — but only up to the edge. The whole method assumes that a backend disagreement is a bug. That is true only when the expected output is backend-independent. Two things can break this assumption. One has already bitten you.
  1. Rendering differences that you have not normalised. The float .0 is one example. They appear as false positives until you normalise them. Handle each one as you find it.
  2. Constructs with true target-divergent semantics. Early on, echoing bit-arrays produced noise. The two backends rendered them differently by design. The fix was not normalisation. The fix was to stop generating bit-arrays as an echo target. Sometimes you must constrain the generator. Do not tune the normaliser.

The --interesting mode is the last piece. It is an exit-code switch. Test-case reducers use it. Interesting means that the input causes a divergence. Keep shrinking the input. Reducers call this switch in a loop. The loop slices the input down to a minimal repro:

if [ "${1:-}" = "--interesting" ]; then
  # Exit 0 iff this input is a divergence.
  [ "$VERDICT" = "MISMATCH" ]
  exit $?
fi

7. Batch campaigns, determinism, resumability

libFuzzer finds crashes. The differential oracle is a separate pass. It generates a seed. It writes the program. It runs the program on both backends. It keeps the source of any divergence. Running one program at a time is slow. Each program needs two full builds and two runs. So you run the programs in batches.

redteam/bin/smith-campaign.sh (essence) 
# Run a batch of seeds: for each, write the program, diff-run it, and keep
# the source of every divergence. Resumable: progress is tracked so a
# campaign can be interrupted and picked up where it left off.
GLEAM_BIN="${GLEAM_BIN:-}"   # pre-built binary fast-path
OUT="redteam/findings/smith"

# Where we left off lives in a state file, so the campaign is resumable.
START="${START_SEED:-$(cat "$OUT/.next-seed" 2>/dev/null || echo 0)}"

for seed in $(seq "$START" $((START + COUNT - 1))); do
  cargo run -q -p gleam-smith -- gen "$seed" > "$OUT/seed_$seed.gleam"
  GLEAM_BIN="$GLEAM_BIN" redteam/bin/diff-run.sh "$OUT/seed_$seed.gleam" \
    | grep -q 'verdict: *MATCH' \
    && rm "$OUT/seed_$seed.gleam" \
    || echo "DIVERGENCE seed $seed kept"
  # remember progress so we can resume after a crash
  echo $(( (seed + 1) % 1000000 )) > "$OUT/.next-seed"
done

Three small pieces of discipline make this usable at scale:

  • Determinism. The function from_seed(n) always yields the same program. A divergence saved as seed_42.gleam is reproducible. You can regenerate it forever. You never lose a bug to randomness.
  • Resumability. A long campaign can get interrupted. A VM reboot can stop it. An OOM can stop it. A crash can stop it. The .next-seed file lets you restart and continue. You do not re-run everything.
  • Keep only divergences. The campaign deletes matches. It keeps only the inputs that produced a mismatch. So the findings directory does not flood with boring programs.

This is where the real bug hunting happens in bulk. It is also the loop that found the known bit-array bugs. It found them many times over a few hundred seeds. Sometimes it found a brand-new bug.

8. Triage: findings, version scope, bisect

Finding a divergence or a panic is the start. It is not the end. Triage turns a finding into a filed, fixed, tracked bug. Most of the judgment lives in triage. One hard rule shapes everything:

A finding is not confirmed until it reproduces against the real gleam CLI. It must not reproduce only against the probe. It must not reproduce only on one backend.

8.1 The findings journal

Every bug gets an entry in redteam/findings.md. Each entry has these parts. The finding number is F-1, F-2, and so on. The minimal repro comes second. The version comes third. The classification comes fourth. The tracker check comes fifth. The current status comes last. The classification is the important habit:

  • confirmed-new-bug: the bug reproduces against the real CLI. It is novel on the tracker. It is ready to file.
  • probe-artifact: the input crashes only in the in-process harness. It does not crash the real compiler. The probe drifted from the real pipeline. This is not a user-facing bug.
  • runner-noise: a false positive. It comes from normalisation, a stale cache, or a version mismatch. It is not a real finding.

Honest labels keep the whole operation trustworthy. The label probe-artifact means that we burned a day. The label confirmed-new-bug means that the compiler is really wrong. Spend the extra ten minutes to label honestly. The time pays for itself many times over.

8.2 Version scope: is it a regression or long-standing?

A bug on unreleased main is an urgent regression. It exists only on main. A bug on the current release is serious. It is a different problem. So the question is this. Does the finding reproduce on the last release?

The script version-check.sh answers this question. It does not disturb the running fuzzing. It builds the released compiler in a throwaway git worktree. It caches the binary. It plays the fixture through the binary. Then it gives a label. REPRODUCES ON <tag> means long-standing. ABSENT ON <tag> means a main-only regression. One design constraint matters. The fuzz loop never invokes this script. So the check cannot affect the running campaign.

Why "is it new?" is not the question. A bug can be long-standing and still novel on the tracker. Nobody filed it before. Long-standing and already-filed are different axes. Review each finding against the tracker. Do not consider only its age. An old compiler can still hide unfiled bugs. Several of the best findings here were present in the release and were unfiled.

8.3 git bisect: which commit introduced it?

When you have a confirmed bug with a clean repro, git bisect finds the introducing commit. It does this automatically. It does a binary search over the history. At each step it runs a script. The script says good or bad. The report then changes. It becomes: commit f366e99, this PR, broke it. That is exactly what a maintainer needs.

# A tiny script that returns 0 for "bug present", 1 for "bug absent".
cat > /tmp/check.sh <<'EOF'
#!/bin/bash
# build this revision of gleam and see if the fixture panics
cargo build -q -p gleam 2>/dev/null
cat /tmp/repro.gleam | ./target/debug/gleam build --target erlang 2>/dev/null \
  | grep -q "Fatal compiler bug"
EOF
chmod +x /tmp/check.sh
git bisect start
git bisect bad HEAD            # current HEAD has the bug
git bisect good v1.18.0        # this release did not
git bisect run /tmp/check.sh   # binary-search to the commit

A bisect to a specific PR is the most useful thing you can give a maintainer. It often reveals the reason. In this session, bisects of several Erlang decision-tree panics landed on one PR. The title was omit unreachable case clauses in Erlang codegen. That title suggested the root cause. Skipping an unreachable clause dropped a variable registration.

Recheck your assumptions. During the session, several findings were assumed to reproduce on the installed 1.18.1. They did not reproduce. The version-scope check exists because this assumption was wrong more than once. Always run the released binary before you classify. Never trust your memory that the release has the bug.

9. Running it forever: the VPS + systemd loop

A fuzzer that runs for one hour is a demo. A fuzzer that runs for months on a cheap VM is a bug-finding machine. The operations layer is minimal on purpose. A systemd unit runs an infinite loop. A daily sync keeps the checkout fresh.

9.1 The infinite loop

redteam/ops/fuzz-loop.sh (essence) 
#!/usr/bin/env bash
# Runs forever, alternating bounded sprints of the fuzz targets and a
# differential batch. Never exits on purpose; systemd restarts it if it does.
set -uo pipefail
ROOT="${REDTEAM_ROOT:-$HOME/gleam}"
cd "$ROOT"

SHORT=900        # seconds per parse_only sprint
LONG=3600        # seconds per codegen sprint
SMITH_BATCH=100  # differential programs per iteration

while true; do
  cargo +nightly fuzz run parse_only -- -max_total_time=$SHORT -timeout=10 || true
  redteam/ops/process-artifacts.sh parse_only || true

  cargo +nightly fuzz run smith_compile fuzz/corpus/smith_compile -- \
    -max_total_time=$LONG -timeout=25 || true
  redteam/ops/process-artifacts.sh smith_compile || true

  cargo +nightly fuzz run compile_all_targets -- -max_total_time=$LONG -timeout=25 || true
  redteam/ops/process-artifacts.sh compile_all_targets || true

  redteam/bin/smith-campaign.sh "" "$SMITH_BATCH" || true
done

Note the || true on every command. A single sprint can fail. A hang can stop it. An OOM can stop it. A toolchain problem can stop it. The loop must never die because of one sprint. Keep going no matter what is the operating rule of a fuzz box.

9.2 The daily sync

A fuzzer is only as good as the code it tests. If the compiler changes and you never rebuild, you fuzz yesterday's bugs forever. The sync job runs daily. A systemd timer starts it. The sync job pulls the latest code. It rebuilds the fuzz targets. It tidies the corpus:

#!/usr/bin/env bash
# redteam-sync.timer -> redteam-sync.service -> sync-job.sh, daily at 04:00.
set -uo pipefail
ROOT="${REDTEAM_ROOT:-$HOME/gleam}"
cd "$ROOT"

git fetch origin
git checkout red-team
git reset --hard origin/red-team

cargo +nightly fuzz build || exit 1   # rebuild harness against new compiler

# minimal libFuzzer needs a working build to shuffle the corpus
for t in parse_only compile_all_targets smith_compile; do
  cargo +nightly fuzz cmin "$t" -feature=redteam 2>/dev/null || true
done

The sync job restarts the fuzz service. So it must run systemctl as root. The fuzz loop runs as a non-root user. The clean way is a tightly scoped sudoers rule (see install-systemd.sh). Let exactly one user restart exactly one service. Let the user do nothing else.

9.3 The systemd units

There are two units and one timer. The fuzz service is the always-on loop. The sync timer nudges it each morning. Three settings matter. Restart=always makes the service self-healing. Nice=10 stops the service from starving real workloads. OOMScoreAdjust=500 makes the fuzzer die first. The fuzzer is best-effort work.

# /etc/systemd/system/redteam-fuzz.service
[Service]
Type=simple
User=redteam
Environment=PATH=/home/redteam/.cargo/bin:/usr/local/bin:/usr/bin:/bin
ExecStart=/home/redteam/gleam/redteam/ops/fuzz-loop.sh
Restart=always
RestartSec=30
Nice=10
OOMScoreAdjust=500

The comment "lose the OOM fight gracefully" is a deliberate choice. A red-teaming box shares resources with production. It must never crash the production box. So the fuzzer is tuned to die first when memory runs out. That one line of judgment is a boring but important detail. It makes months of infrastructure running survivable.

10. Lessons learned, and where the cleverness hurts

If you implement this from scratch, learn these lessons. Some are obvious in hindsight. A few are things that I will change on a rebuild.

10.1 What I will build simpler if I start over

The production generator has accumulated much cleverness. Each piece was added for a reason. A real bug demanded it. But several pieces are more complex than their payoff. A fresh implementation must start without them. Add them only when a bug proves that they are needed:

Cleverness in the current codeWhy it got addedWhat I will do on a rewrite
Shadowing-bias name pools. Found real hygiene bugs. For example, a type collided with the Erlang built-in record. Start with bland unique names. Add hostile names later as a hardening pass.
BindSpec::{Free, One} for alternative patterns. Alternative patterns must bind identical variables. The rule is subtle in Gleam. Defer alternative patterns at first. They are a rich but tricky target.
Bit-array segments with endianness and signedness options. The bugs F-12 and F-13 were :utf8 patterns. The options broaden the surface. The patterns <<_:utf8>> and <<"str":utf8>> alone find real bugs on day one.
Deterministic xorshift seed expansion. Reproducibility is essential. You need determinism. Use a standard seeded RNG. Do not hand-roll the bit-twiddling.

Here is the meta-lesson. Cleverness is debt. You take the debt on when a bug leaves you no choice. A generator with 200 lines of boring code can find one real bug. It is worth more than an 800-line masterpiece that finds the same bug. Start plain. Let the bugs earn the complexity.

10.2 The pipeline-fidelity trap (the most expensive lesson)

The costliest mistake was the probe. It did not mirror the real pipeline. It ran an extra inline module pass. Production does not run that pass. The result was two findings. They crashed in the harness. They never reproduced on a real gleam build. They had to be reclassified as probe-artifact. If you take one lesson from this document, take this one:

The in-process probe is a second implementation of the build pipeline. Like every second implementation, it will drift. Confirm anything the probe reports against the real CLI before it counts. The probe must do the absolute minimum. Ideally it calls the same code as the real build. It must not call a parallel copy.

10.3 The oracle is a trust decision, not a given

Differential testing assumes that backends agree. That assumption is a policy that you set. Keeping the policy costs real effort. You normalise rendering differences. You choose not to generate constructs with target-divergent semantics. Every false positive that you triage is a bug in your model. The bug is in what you call agreement. Keep the model honest and current. If you do not, the signal drowns.

10.4 Label findings like a scientist

The classification keeps the journal trustworthy. The classes are confirmed-new-bug, probe-artifact, and runner-noise. Follow this discipline. Verify against the real CLI. Check the tracker. Note the version scope. Then label the finding. If you skip a step, you will file a non-bug or miss a real one.

10.5 The boring loop is the machine

The generator and oracles are the interesting parts. They are about 30 percent of the work. The rest is the hard part. Build it once. Make it reproducible. Run it forever. Keep it from crashing the box. Keep it honest about what it found. A fuzzer that runs for a month is a bug-finding machine. A clever fuzzer that runs for one hour is a demo. Most of the bugs came from monthly runtime. They did not come from cleverness.

The loop that matters. Generate a program. Run both backends. Compare the output. Keep the divergence. Minimise the input. Check the version. Bisect the history. File the bug. Add it to the known-bugs list. Then the loop does not rediscover it. That is the whole job. You can run the loop by hand. Or you can let a VM run it forever.

11. Further reading & reference list

This project stands on a long tradition of compiler fuzzing. To understand where these ideas come from, start with these references:

  • Finding and Understanding Bugs in C Compilers (CSmith). The paper is the foundation of compiler fuzzing. It defined the method. The method generates well-defined programs and uses differential testing. Read this paper first.
  • wasm-smith. It is the direct ancestor of this generator. It generates valid Wasm modules by construction. Its source is the clearest existing implementation of type-directed generation.
  • libFuzzer documentation. It is short and authoritative. It describes the coverage-guided engine that the crash loop uses.
  • The cargo-fuzz book. It describes the Rust workflow for structured fuzzing with the Arbitrary trait.
  • Delta debugging (Zeller & Hildebrandt, "Simplifying and Isolating Failure-Inducing Input"). This algorithm shrinks a crash to a minimal repro.
  • treereduce. It is a structure-aware reducer. Point it at the --interesting test. It shrinks divergences automatically.
